# 現行スキーマへの再構築

## 目的

地域移行と過去の取得方式に由来するDDL・実行分岐を撤去する。空のDBを単一の現行スキーマで初期化し、Screen TimeをRaw、FitbitをGoogle Health APIから再構築する。既存DBの適用履歴を変更する自動アップグレードは行わない。

## データ構造

Screen Timeのイベント、セグメント、レコード、削除履歴、集計と最新の未完了セグメントを保留する規則は維持する。

Fitbitのbaseは次の5テーブルとする。

| テーブル | 保存する意味 |
| --- | --- |
| fitbit_activity_interval | steps / active-zone-minutes、物理的な開始・終了、値、zone |
| fitbit_resting_heart_rate_daily | プロバイダーの日付、安静時心拍数 |
| fitbit_sleep_session | プロバイダーの日付、睡眠区間、APIの睡眠分数・種別 |
| fitbit_sleep_detail | 睡眠段階と短い覚醒を種別で区別し、親のID・日付と区間を保存 |
| fitbit_heart_rate_minute | APIの1分平均・最小・最大。未知のサンプル数はNULL |

睡眠詳細の長さは区間から算出する。安静時心拍数と睡眠の取得範囲はプロバイダーの日付で判定し、セッションのタイムゾーンに依存させない。睡眠段階と短い覚醒の重なりは保持する。

取得範囲・比較ハッシュは1つのcoverageテーブルにまとめる。新しい取得結果の保護、削除IDの再出現防止、同一内容のDB書き換え省略、完全なRaw内容の比較を維持する。Rawの形式は変更しない。

## 運用

`pdp migrate` は現行DBの初期化と追加DDLの適用を担当する。SQLは `001_current.sql` から始まる1系統のみとし、適用済みチェックサムと未知の履歴を検査する。旧profileや旧migrationを持つDBには書き込まず、空の移行先DBへ再構築する案内を返す。SQLと適用記録は同じトランザクションで確定する。

本番切替は書き込みジョブを止め、新DBを作成、Raw再生とAPI再取得、集計検証の後に接続先を切り替える。旧DBは検証完了まで残す。コードの実装・ローカル検証とは独立して実施する。

## 完了条件

1. パッケージ内に旧地域・旧取得方式のDDLがなく、profile設定も不要。
2. 旧DBへの適用拒否、再実行、チェックサム、失敗時rollback、並行起動後の適用記録を検証できる。
3. Fitbitの補正・削除・日付変更・古いRaw再生・同じIDを持つ異なるmetricの独立性を維持する。
4. 保存済みScreen Time Rawを新DBで再生し、イベント・補助状態・集計を比較できる。
5. 全テスト、lint、型検査、配布パッケージの初期化が通る。

## 再構築検証（2026-10-07）

2026-10-06時点の保存済みGCS inventoryとDBスナップショットを用い、Raw 56件（iPhone 31件、Mac 25件）のSHA-256を検証して新しいローカルDBへ再生した。本番DBとGCSへの書き込みは行っていない。

| 比較対象 | 結果 |
| --- | --- |
| イベント | 80,386件。新しい`loaded_at`を除く全項目が一致 |
| セグメント / レコード / tombstone / deletion match | 24 / 80,386 / 136,956 / 0件、全項目が一致 |
| 取込台帳 | 56件、Raw identity・parser・状態・件数・generation・保持起点が一致 |
| アプリ別 / 端末別の日次集計 | 1,195 / 66行、キー・件数が一致。最大数値差は約1.46e-11秒 |
| Screen Time dbt | 4ビューの生成、33検証に成功 |

Python 3.14の全624テスト、Ruff、mypy、Terraform validate・18個のmock testが成功した。
クリーンなディレクトリで構築したwheelには`001_current.sql`だけを収録し、隔離したPython 3.13環境へのインストール後に共通CLIの初期化・5テーブル作成・再実行を確認した。
FitbitはローカルのAPI fixtureとRaw再生で検証し、実APIからの全期間再取得と本番接続先の切替は未実施である。
